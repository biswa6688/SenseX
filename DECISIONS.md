# Decisions log

Resolved product/architecture questions, in order asked. See ARCHITECTURE.md for how each plays out in code.

1. **ML inference location**: separate Python microservice (FastAPI), not inside NestJS. NestJS orchestrates over HTTP. *Why*: no viable Node-native path to faster-whisper/pyannote/llama.cpp at comparable accuracy.

2. **Model stack**: faster-whisper (distil-large-v3, int8) + Piper + pyannote.audio (speaker-diarization-3.1) + Qwen2.5-3B-Instruct GGUF Q4_K_M via llama-cpp-python, single LLM prompted for summary+sentiment+QA rather than 3 models. *Why*: fits ~10GB of a 16GB CPU-only budget; separate models per task would blow the budget.

3. **Repo structure**: NO monorepo tooling (no pnpm workspaces / turborepo / nx). Plain independent folders: `backend/`, `frontend/`, `ml-service/`, each with own package manager state. No shared-types workspace package — use OpenAPI-generated client instead. *Why*: user explicit preference; also 3 different runtimes anyway so a JS-only workspace tool wouldn't unify them all.

4. **TTS scope**: BOTH (a) pipeline stage reading the generated Summary aloud, and (b) a standalone free-text-to-speech tool in the Playground, unrelated to uploaded-audio analysis. *Why*: user wants both, not either/or.

5. **OpenCode CLI page**: external project — page links to the official upstream OpenCode CLI GitHub releases per platform. No backend hosting/build pipeline, no NestJS module needed for it. *Why*: user confirmed it's the third-party open-source project, SenseX doesn't own/ship it.

6. **Docker**: not used for local dev v1. *Why*: Docker Desktop's WSL2 backend defaults to capping the VM at ~50% of host RAM (8GB on this 16GB machine) — would break the ~10GB model-loading budget unless `.wslconfig` manually raised. Native installs are also easier to debug for torch/ctranslate2/llama-cpp-python build issues on Windows. Revisit later purely for *distribution* (docker-compose for other users), not dev.

7. **Package manager**: npm, independently in `backend/` and `frontend/` (no root install step, no workspace). *Why*: consistent with decision 3 — simplest option once workspaces are off the table.

8. **Python version**: 3.13 for `ml-service`, not the also-installed 3.14. *Why*: 3.14 is too new — no prebuilt CPU wheels yet for torch/ctranslate2/llama-cpp-python at time of scaffolding (2026-08-28). Re-check if bumping later.

9. **Job concurrency**: ml-service pins job-queue concurrency to 1 (never processes two audio jobs at once). *Why*: this — not lazy-loading — is what keeps the app under the 16GB ceiling; CPU inference activation memory can spike per job.

10. **Job history persistence**: dropped Prisma/SQLite. ml-service already writes a `job.json` sidecar per job under `storage/audio-jobs/{jobId}/` as the durability mechanism; NestJS's `AudioJobsService.history()` just lists that shared directory instead of maintaining a second copy of the same state in a DB. *Why*: avoids a duplicate-persistence sync bug class for a local single-user tool; Prisma 7's install was also unexpectedly heavy/slow on this machine and added nothing history-wise that the filesystem didn't already have.

11. **Frontend/backend type sharing**: dropped OpenAPI codegen for v1, hand-written fetch client in `frontend/src/api/client.ts` matching backend DTOs by hand instead. *Why*: time-boxed initial build; codegen wiring (`openapi-typescript` against Nest's `/api-json`) is still the intended end state per ARCHITECTURE.md, tracked as backlog, not abandoned.

12. **Diarization speaker count**: `diarization_num_speakers` defaults to 2, passed as pyannote's `num_speakers` hint instead of leaving it to auto-detect. *Why*: on a real 2-party test call, unconstrained clustering split one speaker across two labels (phantom 3rd speaker) — forcing the known count fixed that specific problem, verified on real audio. This app's QA rubric (greeting/empathy/resolution/compliance) is inherently a 2-party agent+customer framework, so 2 is the right default; set to `None` (env `DIARIZATION_NUM_SPEAKERS`) for multi-party calls.

13. **Diarization model: `pyannote/speaker-diarization-community-1`, not `speaker-diarization-3.1`**. *Why*: on a real 2-party test call, 3.1's plain agglomerative clustering was badly unstable in the full pipeline (transcribe → diarize, in one job) — talk time skewed 190s/9s across 3 spurious turns, most of the call dumped onto one speaker, even with `num_speakers=2` forced. Root cause was never conclusively pinned down (audio input, CPU affinity, and relevant env vars were all checked and ruled out as the mechanism; several process-isolation strategies were tried and reverted, see git history if reviving that investigation). community-1 is a separate, self-contained pyannote pipeline (own segmentation/embedding/PLDA weights, `VBxClustering` instead of plain agglomerative) that produced a correct, balanced result (95.7s/83.2s, 7 turns spanning the full call) on that one test run.

14. **Diarization retry-and-pick-best-balance mitigation** (`DIARIZATION_MAX_ATTEMPTS=3` in `diarize.py`). *Why*: decision #13's fix turned out to be incomplete — community-1's `VBxClustering` does an iterative Variational Bayes refinement (like k-means), and a follow-up real test showed the SAME audio + SAME default settings sometimes reproduces the old bad collapse-to-one-speaker result and sometimes doesn't; it's genuine run-to-run local-optima variance, not something a single config value fixes. Mitigation: run diarization up to 3x, score each attempt by per-speaker talk-time balance (ratio of least- to most-talkative speaker's total time — a real conversation is rarely extremely lopsided, a bad clustering run is), keep the best, stop early once one attempt is "good enough" (balance ≥ 0.3) to avoid always paying 3x the cost. This is a heuristic, not a guarantee — an unusually one-sided real conversation (e.g. a long monologue) could still get a worse score than a bad clustering run and lose out. Revisit if that turns out to matter in practice, or if someone finds the actual source of the clustering non-determinism.

15. **Turn-boundary refinement reuses community-1's own embedding model, not 3D-Speaker/WeSpeaker** (`boundary_refinement.py`). *Why*: a real independent embedding backend was considered (per the diarization-accuracy spec's Phase 8/9) but `wespeaker` isn't on PyPI at all, and 3D-Speaker needs `modelscope`+`funasr` — both installable, but 3D-Speaker itself isn't pip-packaged and pulling it in adds a large, version-conflict-prone dependency stack on an already fragile Windows CPU ML environment (see this session's FFmpeg/torch/ctranslate2 fights). Reusing `diarize.get_embedding_model()` (the pipeline's own `_embedding` submodule) costs zero new RAM — measured: +25MB for a boundary search on a real 68s span, vs the ~570MB the diarization model itself already costs — and no new install risk. Real limitation, not fixed: it's the SAME embedding space as the first diarization pass, so it can't discriminate two speakers the first pass already couldn't. Verified on real audio: correctly declines to force a split when the embedding evidence doesn't support one (both halves of a candidate boundary matched the same speaker centroid), rather than guessing — but on that same test turn it did not confirm the split the user expected either, and there's no ground truth available to say whether that specific turn was a genuine single-speaker monologue (confidence.py false-positiving on length/sentence-count) or a real merge the embedding space can't see. If this turns out to matter often in practice, that's the trigger to revisit 3D-Speaker/WeSpeaker despite the dependency cost.

16. **Reviewed-but-unsplit turns get a `reviewed` flag, not left as bare `uncertain`** (`merge.apply_review_results()`). *Why*: `merge_transcript()` recomputes each turn's confidence purely from duration/sentence-count (confidence.py) — it has no memory of decision #15's embedding-based re-check having already run. Without this, a turn that boundary_refinement.py actually verified (found no evidence of a missed speaker change) still showed the same unexplained "UNCERTAIN" warning as one nobody ever checked — indistinguishable to the user, and looked like the refinement step had no effect. Fix: turns in `checked_no_split_spans` (returned by `refine_diarization_turns`) get `uncertain=False`, `reviewed=True`, confidence bumped to 0.65 (not 1.0 — corroborated by a second signal, not verified ground truth). Verified on real audio: the known problem turn now shows `reviewed` instead of a bare `UNCERTAIN`.

17. **Escalated to 3D-Speaker after all (`three_d_speaker.py`), superseding part of #15** — user asked directly to escalate once #15's "reuse community-1's own embedding" approach left the known test turn unresolved. *Why this works where #15 didn't*: it's a genuinely different architecture (ECAPA-TDNN/SDPN, trained on VoxCeleb English data) — an actual independent signal, not the same embedding space checking itself. Verified on the exact same real test turn: found a sharp similarity drop (0.297, vs a 0.6-0.97 baseline) at t=104.6s that community-1's own embedding never surfaced, and the two halves matched DIFFERENT known speakers (0.71 vs 0.65, and 0.74 vs 0.63) — a genuine, corroborated split, not a guess.
    Real install friction encountered and resolved, in order: (a) `wespeaker` still isn't on PyPI, ruled out again; (b) modelscope's own import chain needs `addict`, `datasets`, `simplejson` as undeclared transitive deps — pinned explicitly in requirements.txt rather than relying on them installing incidentally; (c) the specific SDPN checkpoint's `torch.load()` call breaks under PyTorch 2.6+'s `weights_only=True` default — `add_safe_globals` doesn't fix it (the pickle encodes the pre-numpy-2.x `numpy.core.multiarray.scalar` path string, which doesn't match how torch resolves the allowlisted object's real `__module__`) — worked around with a narrowly-scoped `torch.load` monkeypatch during just this one model's load, restored immediately after. None of this touched the app's existing torch/numpy/ctranslate2 versions — dry-run confirmed zero conflicts before installing anything.
    RAM: measured ~560MB resident once loaded (checkpoint is ~343MB on disk) — lazily loaded only when `boundary_refinement.py` actually needs a second opinion, not resident by default. `three_d_speaker.get_embedding_model()` is now tried first for refinement, falling back to `diarize.get_embedding_model()` (community-1's own, #15) if 3D-Speaker fails to load (e.g. offline on first download) — never a hard dependency, the pipeline still completes without it.

18. **Ground-truth comparison surfaced two more real errors; fixed one, root-caused a second** — user compared our transcript against an independent transcript of the same call. (a) `merge.py`'s gap-word fallback now resolves gaps by comparing the gap's own voice against both adjacent turns instead of picking whichever is closer in *time* — fixes one real class of misattachment, though the specific "Perfect." case from the comparison turned out NOT to be a gap word (see #19). (b) `boundary_refinement.py` now checks any turn ≥4s (`MIN_CHECK_DURATION_SECONDS`) regardless of confidence.py's flag, since a real merge can be short enough to never trip that heuristic — verified this catches a merge that was previously invisible to refinement entirely. Broadening that check trigger introduced a real regression, caught via the diagnostic trace the user's plan asked for: the "confident" pool used for centroid-building got redefined to exclude every check-candidate turn too, not just uncertain ones, starving it down to a single speaker on one real job (so every left/right comparison trivially "agreed" and no split could ever apply). Fixed by decoupling "should this turn be scanned" (`needs_boundary_check`) from "is this turn a valid centroid reference" (back to confidence.py's original `uncertain` flag only) — these are different questions and conflating them was the bug.

19. **Short-span speaker resolution (`short_turn_resolver.py`) — multi-signal, and NOT a hardcoded word list**. *Why*: the ground-truth comparison (#18) also showed a genuine diarization-stage misclustering of a single ~0.87s word ("Perfect.") — directly covered by a real (but wrong) raw diarization turn, not a gap, and too short for a reliable voice-embedding classification on its own (confirmed: sub-1s clips don't carry enough acoustic signal for confident speaker discrimination in any embedding model). First version used a hardcoded English backchannel word list ("perfect", "okay", "sure", ...) for the linguistic signal — user directly called this out as still a hardcoded special case, just a bigger one, and pointed out it wouldn't generalize to other languages or unlisted phrasing. Replaced with a call to the already-loaded LLM (Qwen2.5-3B, already resident per this app's eager-load design — zero new RAM) asking whether a candidate short utterance reads as an acknowledgment/backchannel vs. a substantive continuation — a real language-model judgment instead of a lookup table, only invoked for candidates that already passed structural pre-filtering (short duration, sandwiched between one other speaker on both sides), so it fires rarely enough per job to stay within the "fast and accurate within 16GB" budget. Combines linguistic + position + pause + acoustic-similarity into one score; reassigns only above a high combined threshold, never on one signal alone.

20. **Multi-boundary change-point detection (`long_turn_refiner.py`), replacing single-boundary bisection in `boundary_refinement.py`**. *Why*: `refine_diarization_turns()` previously found only the single strongest similarity drop in a candidate turn and split it in two — correct for one missed speaker change, but a genuinely long turn can contain MORE THAN ONE (e.g. a short customer confirmation buried inside a long agent explanation), and iterating the old single-split logic across rounds only ever re-checks the *remainder* of a previous split, never a short middle segment whose surroundings on both sides still look like the original speaker. `long_turn_refiner.refine_long_turn()` instead scans the whole window trajectory for a candidate turn, collects every local-minimum similarity drop below threshold (not just the global minimum), and independently reclusters each resulting segment against the known speaker centroids, collapsing adjacent segments that reclustered to the same speaker back together. Verified on the real known-problem call: a 76.7s block (95.2-171.9s) that the old logic left as one turn was correctly found to contain an internal boundary at ~96.45s; the 1.25s leading segment ("Just check that.") was still acoustically misclassified by the centroid comparison alone (too little audio for the embedding to discriminate confidently — the same limitation noted in #15/#17), so `short_turn_resolver.py` gained a third pattern (leading sub-span of a longer run, preceded by a different speaker — the mirror of its existing trailing-sub-span pattern) to catch it at the word level using the same multi-signal scoring. Combined, the two fixes correctly reassign "Just check that." to the customer, matching independent ground truth. Also verified the detector is appropriately conservative: on the remaining 74.7s single-speaker block in the same call, it proposed two candidate boundaries (105.85s, 169.35s) but every resulting segment reclustered to the *same* speaker centroid, so it correctly declined to split rather than force a change.
    Known remaining limitation, not fixed here: `refine_transcript()`'s round budget (`MAX_REFINEMENT_ROUNDS=3`) can be exhausted by a turn newly created in the final round, leaving it with confidence.py's raw (low) confidence/uncertain flags even though a same-speaker recheck would have cleared them — a bookkeeping gap, not a transcript-text error (confirmed by re-running the check manually on that exact turn post-hoc: it still declines to split). Not user-visible since the `uncertain`/`reviewed` badges were removed from the UI; revisit if the raw confidence field is ever surfaced again.

21. **Fixed a real word-covering-turn bug in `merge.py`'s `_assign_speakers()`: overlapping raw diarization turns silently discarded the shorter one**. *Why*: pyannote turns can genuinely overlap — a short interjection from one speaker nested inside a longer turn from another — and the covering-turn lookup was `next(t for t in sorted_turns if t["start"] <= midpoint <= t["end"])`, i.e. the FIRST turn by start time that contains a word's midpoint. Since the longer, earlier-starting turn always sorts first, any word whose midpoint fell in the overlap always got that turn's speaker, silently discarding the shorter nested turn every time. This is the actual root cause behind the user's report that a long block "still" wasn't segregated after #20: raw diarization on the real problem call had ALREADY detected a genuine ~0.63s SPEAKER_01 turn (144.68-145.31s) nested inside a SPEAKER_00 turn (144.48-145.43s) — visible directly in `diarize.diarize()`'s raw output — but it never reached the transcript because the covering-turn lookup threw it away before word assignment even started; no amount of downstream refinement (#20) could recover a turn that was discarded before refinement ever saw it. Fixed by picking the *narrowest* covering turn instead of the first one — the more specific match for that exact word. Verified on the same real call: the nested interjection now survives into the final transcript.

22. **`short_turn_resolver.py` gained an acoustic veto** (`ACOUSTIC_VETO_THRESHOLD`), after #21's fix surfaced a second real bug in the multi-signal scoring itself. *Why*: once the nested SPEAKER_01 turn from #21 survived into the word-level runs, `short_turn_resolver`'s pattern 3 (leading sub-span, added in #20) evaluated the following SPEAKER_00 words ("Actually, that slot") as a candidate to trim onto SPEAKER_01 — and wrongly reassigned them. Breaking down why: the linguistic LLM judged "Actually, that slot" (a clear sentence continuation) as a backchannel and scored it 1.0; combined with `WEIGHT_POSITION`'s unconditional 0.30 credit and a real-but-coincidental 0.94s pause, the weighted sum cleared `REASSIGN_THRESHOLD` even though the acoustic signal (0.205 — the run's own voice matched the *current* speaker's reference far better than the candidate) was flatly against it. The weighted-sum design let three soft, contextual heuristics (linguistic/position/pause) outvote the one signal actually grounded in the run's own voice. Fix: acoustic now vetoes outright (returns 0, ignoring the other three signals) when it's confidently opposed (< 0.35), rather than just being one more vote — it only blocks, never promotes, so a neutral/unavailable acoustic reading (>= 0.35) still lets the other three decide normally. Verified on the same real call: "Actually, that slot is not available..." now correctly stays with SPEAKER_00, while the genuinely nested "a minute." stays SPEAKER_01 (from raw diarization, #21 — not independently confirmed against ground truth, since it's a 0.5s fragment inside a longer sentence and there's no way to verify without listening to the audio).
